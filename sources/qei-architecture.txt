Corpus model

Every ingested item should have common metadata.

For example:

{
  "source_type": "jira",
  "source_id": "KAT-1499",
  "project": "BSP",
  "domain": "Payments",
  "document_type": "acceptance_criteria",
  "authoritative_level": 5,
  "updated_at": "2026-09-01",
  "access_scope": "project:BSP",
  "url": "...",
  "content": "..."
}

The same basic structure applies to:

jira
confluence
sharepoint
bitbucket
slack
katalon
testops
Evidence authority model

This should be implemented in Week 2, not just documented.

Level 5 — Authoritative
Approved Jira AC
Approved Confluence specification
Approved SharePoint design
Organization QE standards
Level 4 — Implementation truth
Current merged application source
Current Katalon automation
API contracts/schema
Level 3 — Execution evidence
TestOps results
CodeBuild execution
PR review findings
Level 2 — Supporting context
Jira comments
Slack discussions
Historical project notes
Level 1 — Historical / weak

Old or superseded information.

The LLM itself is:

Level 0 — inference only

AI inference can explain evidence but cannot become authoritative evidence.

Week 2 project awareness

This is essential.

CXE
Type: UI
Testing strategy: User Journey

Salesforce
Type: UI
Testing strategy: User Journey / Business Process

BSP Services
Type: API
Testing strategy: Risk-Based

SPROG
Type: API + UI
Testing strategy:
API / UI / API_DB / UI_DB / HYBRID / E2E

So the same question can produce different analysis based on project.

Example:

Analyze test coverage for this change.

For BSP:

Requirement
→ Risk
→ API contract
→ Authentication
→ Negative coverage
→ DB validation
→ Regression

For CXE:

Requirement
→ affected user journey
→ current journey coverage
→ reusable objects
→ UI regression impact

We don't evaluate only answer quality.

We'll test the QE intelligence system like a QE system.

VERIFIED
